# 性能基线与回归定位（2026-10-31）

## 环境

- Windows 11 x64，Ryzen 5 9600X（12 逻辑核心），RTX 3070，驱动 621.01
- Release 便携版，共享同一份 `data`（7 个游戏，封面缓存预热，`showCovers=true`）
- 测量：进程启动后 50–60 秒，`Get-Process FrameGenManager-Next` 的 Working Set
- 说明：本机 `\Process(...)\Working Set - Private` 计数与 Task Manager 不一致，本轮先统一使用 Working Set 做相对比较；后续脚本改为 CIM 私有工作集 + 子进程过滤

## 二分结果

| 版本 | 说明 | 宿主 Working Set |
|---|---|---|
| `8fbfeb6` | 内存改动之前 | 149–152 MB |
| `6b4f006` | 加入 JS 堆上限、GC Conserve、`MemoryUsageTargetLevel.Low`、工作集修剪 | 263 MB |
| `6a856d8` | 移除 Low、页面切换已还原 | 268–270 MB |
| 当前 + 去掉逐游戏 NVAPI 查询 | 仅用于定位 | 148.5 MB |
| 当前 + NVAPI 批量会话（库页） | 一次会话读全部游戏 | 171.9 MB |
| 当前 + 库页/SM 页都批量 | 一次会话 | 176.9 MB |

结论：**不是封面，也不是 `MemoryUsageTargetLevel.Low`**。主要回归是“每个游戏开一次 NVAPI DRS 会话”：

- 每次 `NvApiSession.Open()` 都会 `DRS_LoadSettings`，驱动把整份 profile 数据库加载到原生内存；
- 库页 7 个游戏 = 7 次加载，SM 页再 7 次，原生内存约 +100 MB 且不随托管 GC 回收；
- 改成一次会话批量读取后，重启即回到 170 MB 左右（封面仍开启）。

之前的封面 A/B 受页面加载阶段和 NVAPI 调用重叠影响，不能作为结论；已在文档中更正。

## 已实现

- `INvApiSmoothMotion.GetStatesAsync`：单会话批量读取多个 EXE。
- 帧生成页状态：整库一次批量读取。
- Smooth Motion 页：一次批量读取，`InspectAsync` 接受预读结果，不再逐游戏开会话。

## 复现命令

```powershell
# 共享数据目录
$env:FGM_DATA_DIR = 'D:\fgm-perf-wt\data'

# 启动并等待 50 秒
$p = Start-Process -FilePath '<exe>' -PassThru
Start-Sleep -Seconds 50
(Get-Process 'FrameGenManager-Next').WorkingSet64 / 1MB

# WebView2 进程需按父进程链过滤，不要把其它浏览器的 msedgewebview2 算进来
Get-CimInstance Win32_Process -Filter "Name='msedgewebview2.exe'" |
    Select-Object ProcessId, ParentProcessId, CommandLine
```
